# 10 依赖、许可证与供应链

适用：JS/Rust 依赖、shadcn 注册表源码、CI actions、下载工具/sidecar 与发行资源。消费包负责人解释必要性与升级影响，构建/发布负责人维护来源和产物关联，安全/许可证职责映射到实际组织维护者；不要求模板预装全部扫描平台。

## SUPPLY-VERSION · 引入与版本策略

- **必须**记录新增运行依赖的用途、维护来源、许可证、运行环境、实际兼容与替代方案；同职责已有工具时解释增加第二种的理由。高权限原生插件、安装脚本、sidecar 和认证库按其能力审查。
- **默认**优先官方/稳定维护源，版本与 lockfile 关联；普通版本范围可用于开发声明，但 CI/发布从冻结 lockfile 构建。CLI 生成结果记录可追踪的源和所用版本，不认为生成后就没有第三方许可义务。
- **必须**同时治理直接与传递依赖、Cargo features、平台条件依赖及 build dependencies。仅更新 package.json、不分析锁文件和原生 crate，无法证明发行依赖已更新。
- **默认**功能修复/漏洞补丁与大版本迁移分开处理，自动更新可生成评审变更，验证仍按实际影响执行。deprecation 有替代/退出计划，override/patch 有负责人、上游问题、适用版本与撤销条件。

## SUPPLY-CI · CI 与外部二进制来源

- **必须**外部下载固定版本/平台/来源，并验证可信签名或有可信来源的预期 digest；不能发布时拉取未固定的 latest，或只与同一个可变下载位置提供的任意 hash 比较就宣称可信。
- **默认**生产 CI 的第三方 action 固定完整 commit SHA，版本升级保持审查和功能验证。限制 token 权限，发布签名步骤和不受信 PR 测试分离；不受信代码不能接触发行凭据。
- **必须**不将来自 PR 标题、分支名、issue 文本等不受信输入插入可执行 shell；安装脚本与注册表代码也是执行面。按照锁定的 pnpm 版本使用相应 install/build-script 控制，具体配置核对当前官方行为。
- **必须**记录 sidecar 的版本、目标 OS/架构、许可证、获取/校验方式、bundle 路径和执行权限，并验证退出/失败与生命周期；npm lockfile 不会自动固定单独下载的二进制。

## SUPPLY-VULNERABILITY · 漏洞处理与例外

**必须**有按风险执行的处理流程：发现 → 识别实际包/版本/平台与构建/运行作用域 → 判断可达性、利用条件、暴露面与补救 → 设定优先级/期限/负责人 → 修复或有期限例外 → 验证发行产物与关闭记录。

| 结果                                         | 默认门禁                                               |
| -------------------------------------------- | ------------------------------------------------------ |
| 凭据泄漏、可信来源失效或确认可利用的重大缺陷 | 停止受影响的发行/使用范围，撤销/轮换或隔离，并验证修复 |
| 匹配且有实际风险的漏洞                       | 按组织明确 SLA 修复/减轻；期限到期进入升级或门禁流程   |
| 不匹配版本/目标平台、不可达路径、误报        | 记录判断证据；精确抑制与复查触发条件，不全局关闭扫描   |
| 尚未判断                                     | 可见的待处置状态、负责人和时限，不能当作无风险通过     |

组织为风险等级定义非空的响应/修复期限；不把任意通用 CVSS 阈值等同业务风险。dev/build 依赖也可能影响构建完整性，不能只因不进 bundle 就忽略。例外包含 advisory ID、版本/范围、理由、补偿、负责人和到期，沿用治理章节。

## SUPPLY-LICENSE · 许可证与发行可追溯性

- **必须**建立许可清单与所需 notices，包含复制的组件源码、字体、图标、sidecar、Rust 与传递依赖；允许类型与义务按组织规则核实。不在本技能推定所有 MIT 以外许可不可用，或提供个案法律结论。
- **生产发行默认**生成与实际候选产物对应的 SBOM（选择 SPDX/CycloneDX 等现有格式），记录源码 commit、lockfile、toolchain、平台、构建任务、产物 digest 和签名；开发源码依赖清单不能代替完整发行构成。
- **按供应链要求**附 provenance/attestation 和验证流程；使用签名、SBOM 或某 CI 产品不会自动达到某个 SLSA 等级，需要对应实际信任边界与构建证据。
- **必须**让测试/扫描、签名与分发指向同一候选产物，分发端能检查更新签名/完整性。可重建性、字节完全可复现与可追溯是不同能力，签名/时间戳导致字节变化时说明保证范围。

## SUPPLY-ACCEPT · 验收证据

引入/升级提供真实消费者与目标平台兼容验证；供应链变更验证固定来源、篡改/校验失败、无凭据 PR 运行和许可输出。漏洞处理记录不能仅粘贴扫描分数；发行记录关联实际 SBOM、digest、签名/来源证明和例外。
