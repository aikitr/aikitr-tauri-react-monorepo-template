# 03 错误、日志与可观测性

适用：所有生产应用需要可诊断错误；远程 telemetry、crash reporting 和审计仅在产品确实需要时启用。feature/domain 定义业务错误语义，适配器转换第三方/IPC 错误，应用呈现反馈；平台负责人维护日志管道，服务负责人维护服务端指标与告警。

## OBS-ERROR · 错误契约与处理责任

| 类别               | 默认 code 示例                                     | 默认处理                               |
| ------------------ | -------------------------------------------------- | -------------------------------------- |
| 用户取消           | `CANCELLED`                                        | 收敛任务状态；通常不弹失败 toast       |
| 输入不合法         | `VALIDATION_FAILED`                                | 字段或操作上下文提示，不自动重试       |
| 身份/权限          | `UNAUTHENTICATED` / `FORBIDDEN`                    | 按会话策略处理；权限失败不当成网络故障 |
| 版本/资源冲突      | `CONFLICT` / `NOT_FOUND`                           | 刷新状态或提供冲突处理，不盲目覆盖     |
| 暂时不可用         | `TIMEOUT` / `UNAVAILABLE`                          | 符合幂等和业务语义才有界重试           |
| 存储/协议/内部错误 | `STORAGE_FAILED` / `INVALID_RESPONSE` / `INTERNAL` | 安全反馈、诊断标识、恢复或明确停止     |

这些 code 是团队默认，项目可采用现有一致契约。**必须**用稳定 code 驱动逻辑，不解析本地化 message 判断失败类型。外部接口只返回安全字段（code、可展示 message key/参数、correlation ID）；栈、SQL、完整路径、凭据和第三方原始返回保留在受控内部边界。

- **必须**确定一层负责用户提示、一层负责记录最终失败。上游重试不重复报告每次预期失败；ErrorBoundary、异步请求、原生初始化/任务失败各自有明确入口。
- **默认**保留内部 cause 链，适配器把非 Error 的 IPC reject 规范化；恢复操作同样记录是否成功。UI 的 retryable 只是提示，不能绕过业务幂等约束。
- **必须**预定义关键故障的恢复路径：初始化不可用、持久化失败、协议不兼容、权限拒绝。任何“继续”动作能说明对数据和任务的影响。

## OBS-LOG · 结构化日志与跨边界关联

**默认记录字段**：UTC 时间、severity、应用版本/build ID、组件或 domain、event 名、operation/request ID、duration、结果 code；多窗口另有 window label，任务有 job ID。使用 trace 时保持合法 trace/span 关联。不要让普通用户 ID、路径、完整 query 或错误 message 成为高基数 metric label。

- **必须**令同一次用户操作的前端、IPC、Rust、HTTP 请求能通过非敏感 correlation ID 关联；该 ID 不是身份、授权或可信业务参数。
- **默认**DEBUG/TRACE 仅本地开发或期限明确的诊断模式；生产 INFO 记录关键状态变化、WARN 记录可恢复异常、ERROR 记录未完成操作/内部失败。避免每次渲染、循环或高频进度生成无限日志。
- **必须**选择统一日志路径和输出方式，控制单文件大小、总容量、保留期限和轮转；数值由支持需求与设备资源确定并记录。日志满、磁盘满或远端不可用不能拖垮主业务；必要审计另定义失败策略。
- **必须**采用字段白名单和源头脱敏，禁止 token、密码、Cookie、私钥、授权码进入日志；文件内容/完整个人路径默认排除。仅靠上传时的字符串替换不能保证原始落盘数据安全。

## OBS-DIAGNOSTICS · 诊断、遥测与审计

- **默认**本地诊断先具备脱敏导出能力：包含版本/平台、有限时间段、错误码和必要状态，限制数量/大小，用户能了解导出内容。不要自动打包全部用户目录或数据库。
- **启用远程采集时**记录目的、字段、接收方、采样、保留/删除、用户设置与组织策略；使用适用的数据治理流程确认采集范围。上传关闭时停止采集/发送对应数据；离线缓冲有容量和期限，不无限排队。
- **crash reporting**检查 dump、breadcrumbs 和 source maps 的敏感性；调试符号按 build ID 私有管理。禁用或删除客户端日志不能保证服务端已存内容同时删除，需要接收端对应流程。
- **需要审计时**按操作记录主体、对象、结果和时间，最小化敏感值；客户端可改日志不具备不可抵赖性。权威审计在可信后端或专门受保护的通道实现，不把普通 debug log 宣称为审计系统。
- **部署服务端时**定义关键成功率/延迟指标、适用 SLO、告警负责人和处置 runbook。纯桌面离线产品可使用诊断与发行质量数据，不为套模板搭建整套监控平台。

## OBS-ACCEPT · 验收证据

至少能复现一次跨前端/原生的故障并关联记录；检查正常/错误/取消路径的提示次数和脱敏。验证日志轮转、容量上限、采集关闭、离线上传上限和诊断导出内容。验收材料是安全日志样例、字段/保留配置、恢复步骤；启用远程采集时补充数据流与接收方验证。

日志实现和结构化字段依据见 [资料来源](sources.md)，重试语义见 [数据规范](data-and-native.md) 与 [同步规范](offline-and-sync.md)。

诊断/遥测数据的访问、保留、删除副本及完成状态见 [数据生命周期](privacy-and-data-lifecycle.md)。
