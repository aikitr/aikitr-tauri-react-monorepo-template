# 17 规范落地、模板与维护机制

适用：将本技能映射到实际仓库的工程约定、门禁与证据。规范维护者负责版本和条款，模块所有者维护控制，CI/发布负责人保管结果。使用现有文档/工单/流水线，不强制新建治理服务，也不因生成模板就自动修改项目或远程规则。

## STD-ADOPTION · 能力清单与渐进落地

1. **必须**先确认当前能力、产品承诺、现有约束和实际所有者，列出适用/未启用/待验证项。模板、生产桌面与受管分发采用不同范围。
2. **默认**记录实际基线与目标差异；优先数据/授权/构建正确性，再落实跨模块契约和实际发行要求。已有有效默认约定可保留，不为了“目录标准化”同时重写路由、状态和组件底座。
3. **必须**让每个被采纳要求具有负责人、控制位置、验证和处置路径；映射尚未实现时标为待落实，而不是声称 CI 已 enforce。
4. **默认**在相关变更/发行时收集必要证据；没有变化且输入相同的可复用结果说明依据，不能用过期结果代表新提交或新配置。

## STD-MAPPING · 规则、机器检查与人工证据

最小映射：稳定规则组 ID＋具体条款/等级＋规范修订 → 启用条件/精确范围 → 所有者 → 实现控制与检查 → 检查性质/环境/输入 → 证据 → 状态 → 例外/下一步。可用 [规则检查映射模板](../assets/templates/rule-check-mapping.md)。

- **必须**区分自动阻断、自动提示、人工验收、未落实与不适用；配置了规则或存在脚本不代表已运行。标题/标签用于选择检查，不能代替检查行为、结果或真实依赖图。
- **必须**验证必需 job 选择和实际执行；未选中、零测试、skip、缓存来源不明、工具链缺失或异常中止保持可见。规则本身用正常与真实违规样例验证，避免正则仅查文字或检查永远成功。
- **默认**复用 exports、类型、lint、图分析和现有 CI；高影响真实能力采用相应集成/人工证据，不承诺自动化所有 OS 与组织流程。
- **必须**把评审状态和证据状态分开：设计已批准、控制已实现、检查已运行通过、例外已接受各有含义。风险接受不改变测试失败事实，也不授予实际发布或外部变更权限。
- **采用机器判定验收时必须**定义必填与条件字段、允许状态和候选/输入关联的结构，并验证缺字段、失败、未运行或不适用无理由时不会误判通过。普通人工 Markdown 记录不要求另外引入 schema 工具；模板文件存在不等于机器校验已实现。

## STD-TEMPLATES · 可复用交付模板

模板属于生成输出资产，按当前任务选择读取/复制；字段提示需替换为实际内容，未填写视为未知/待验证，不自动通过。低风险变更可删减不适用段，但保留真实结果与不适用理由。

| 资产                                                      | 默认仓库位置/使用时机                           |
| --------------------------------------------------------- | ----------------------------------------------- |
| [PR 评审](../assets/templates/pull-request.md)            | .github/pull_request_template.md 或现有评审载体 |
| [ADR](../assets/templates/architecture-decision.md)       | docs/adr/NNNN-decision.md；长期跨模块决定       |
| [规范例外](../assets/templates/standards-exception.md)    | 现有 issue/例外登记；精确范围与复查             |
| [兼容矩阵](../assets/templates/compatibility-matrix.md)   | 产品支持文档/发行记录；平台、协议与 schema      |
| [发布验收](../assets/templates/release-acceptance.md)     | 当前候选产物的发行记录；不预设上线授权          |
| [恢复演练](../assets/templates/recovery-exercise.md)      | 适用能力的 runbook/演练结果                     |
| [规则检查映射](../assets/templates/rule-check-mapping.md) | 仓库规范入口/实际门禁映射                       |

**默认**在采纳规范时仅复制本次需要的模板并适配实际流程，不批量制造空文件。工程模板内不保存凭据、用户原始数据或无限诊断附件；生成/填写也不自动创建 issue、发送消息或触发发布。

## STD-REVISION · 修订、兼容与退役

- **默认**通过已有版本控制/文档修订标识管理规则变化，记录日期、理由、影响范围、负责人、迁移和复查触发器。无需为每个小文案变化发布新包；未在 Git 的技能可用维护日期/内容修订记录，并由项目采纳时固定可追踪版本。
- **必须**保留稳定规则组 ID；拆分/合并建立旧→新映射，退役标记替代关系与适用历史，不重编或复用。等级提升、能力范围或正确性条件改变是实质规则变化，不能仅作为格式更新悄悄追溯判定旧项目违规。
- **默认**实质变化设置产品风险决定的迁移期限和分阶段门禁；严重实际风险按安全/发行门禁处理，不因宽限期自动允许不安全能力发布。已接受例外关联原规则修订与复查，规则改变时重新判断其适用性。
- **必须**规范复查有所有者和明确触发：框架/插件升级、支持平台变化、公共契约/权限变更、事件复盘和例外到期。生产团队默认另定有期限的周期复查；频率由变更风险确定，不规定统一月份。旧资料归档并标记停止适用，避免多个“最新版”冲突。

## STD-ACCEPT · 落地验收

选择一项真实边界检查和一项人工验收，验证正常/违规/未运行/不适用状态、当前输入与证据关联、例外到期后的可追踪处理；检查规范更新时旧引用仍可解释。已有相关控制可直接核验，不人为部署新流程。

交付能力清单、差异顺序、实际映射、所用模板/修订、当前证据和未落实项；只交付规范时不能标记项目已通过。责任与例外细则见 [协作治理](collaboration-and-governance.md)，检查分级见 [工程交付](tooling-and-delivery.md)。
