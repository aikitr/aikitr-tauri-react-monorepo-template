# 02 本地存储、迁移与恢复

适用：存在配置、业务数据、持久化队列或数据库的应用。数据所属 feature/domain 定义模型和保留策略，平台层实现存储，Rust/后端协调真实写入；应用启动层协调迁移。具体使用 JSON、Tauri store、SQLite 或其他数据库按访问模式决定，不预装数据库。

## STORAGE-OWNERSHIP · 分类、位置与所有者

| 类别                | 默认位置/语义                                  | 必须约定                                         |
| ------------------- | ---------------------------------------------- | ------------------------------------------------ |
| 安装资源            | 只读随包资源目录                               | 不作为用户数据写入位置                           |
| 用户偏好            | OS 应用配置目录                                | 默认值、版本、损坏恢复；漫游与设备专属项分开     |
| 业务数据/本地数据库 | OS 应用数据目录；不漫游数据选择相应 local 目录 | 账户/工作区隔离、唯一写协调、保留与备份          |
| 可重建缓存/索引     | OS 应用缓存目录                                | 大小上限、失效、重建与清理；删除不能损失唯一数据 |
| 日志/临时数据       | 应用日志目录/安全临时目录                      | 轮转、期限、清理、文件权限及敏感信息             |
| 凭据/加密密钥       | 明确选定的凭据/密钥存储                        | 解锁、访问范围、轮换与丢失后的恢复能力           |

**必须**通过平台路径 API 获取位置，不依赖 cwd、仓库路径或安装目录可写。application identifier 变化导致存储路径变化时有迁移策略。所有者必须能说明“谁写、谁读、谁删、能否重建”；缓存、备份或普通文件名不是加密/授权措施。

## STORAGE-WRITE · 写入、一致性与并发

- **默认**多窗口访问同一可变数据经原生业务接口协调；窗口发送操作/patch 和期望版本，不独立读改写整个 JSON。必要时采用 revision/比较交换或事务，冲突返回可识别结果。
- **必须**明确单进程与多进程的范围。单实例、内存 mutex、JS store 不能保证其他进程不写；允许多进程时使用数据库锁或已验证的文件锁与冲突协议。
- **必须**使文件保存符合已承诺的完整性、一致性和崩溃恢复语义。**默认**先验证/序列化，再写同目录临时文件，按承诺的持久性同步并以目标平台支持的方式原子替换，保留可恢复的旧版本策略。原子可见性与断电持久性是两个要求；rename 成功不能独自证明断电后完整。替代实现须提供相同语义的证据，在支持的文件系统验证。
- **必须**让数据库中需要原子提交的相关修改在事务内提交；设置锁等待期限、失败映射和连接释放，检查约束与索引。跨文件系统和数据库的操作无法凭普通 SQL 事务获得全局原子性，必须定义失败与重启后的对账恢复；**默认**用操作日志、检查点或补偿实现。
- **默认**业务 SQL 和写授权留在原生/后端 domain，不向 UI 暴露通用执行任意 SQL 的命令。确需客户端 SQL 插件时记录威胁模型、权限与访问边界，不能假设插件替代业务授权。

## STORAGE-MIGRATION · Schema 迁移与版本兼容

1. **必须**为存储格式记录独立 schema version；迁移文件有稳定顺序/标识，已发行迁移不原地修改。数据库/偏好版本不等同于应用版本。
2. **必须**先迁移再开放相应读写；迁移只有一个协调者。验证存量脏数据、默认值、约束、耗时、磁盘空间和中断恢复；可事务化的步骤事务执行，长流程分阶段记录检查点。
3. **默认**兼容变更优先扩展 → 迁移数据 → 更新消费者 → 收缩旧结构。删除列、改变含义和加约束需显式兼容分析；多版本客户端和远端 API 同样适用。
4. **必须**发布兼容表：旧数据→新应用、新数据→旧应用是否支持，最低读取/写入版本，以及失败时的恢复方式。旧程序看到更高的不兼容版本时拒绝写入并保留数据，不能重置默认值覆盖。
5. **必须**区分回滚二进制与回滚数据；没有验证过旧版本读取/写入迁移后的数据，就不能承诺降级。不可逆迁移优先前向修复或从兼容备份恢复；恢复可能丢失备份后修改，必须说明。

## STORAGE-RECOVERY · 备份、恢复与损坏处理

- **默认**重要且不可重建的用户数据定义备份方式、加密/访问范围、保留份数、恢复点与恢复时限。恢复要求来源于产品承诺，团队记录实际目标，不照搬统一 RPO/RTO 数字。
- **执行 SQLite 在线备份时必须**获得一致且可恢复的快照；**默认**采用 Online Backup API、合适的 VACUUM INTO 或经过验证的一致快照方案。活跃 WAL 数据库只复制 `.db` 可能漏掉已提交记录；同步复制 `.db` 和 WAL 也不能自动保证一致时间点。不要手工删除 WAL 作为修复。
- **必须**校验备份格式/完整性，在隔离位置实际恢复并运行业务检查后再替换活动数据；备份记录 schema、应用版本、时间和完整性信息，不包含无必要的凭据。
- **必须**区分可重建缓存损坏与唯一业务数据损坏。缓存可删除重建；业务数据先保留原文件、停止不安全写入、提供诊断和恢复路径，不能静默清空。
- **按需**提供导入/导出；导入视为不受信输入，校验格式、版本、大小和路径，清楚定义合并、替换、重复项及中断行为。

## STORAGE-ACCEPT · 验收证据

测试覆盖并发/过期版本写入、磁盘满、权限拒绝、写入中断、损坏输入、旧版本升级、迁移重复/中断、活动数据库备份与恢复。宣称支持降级时额外使用真实旧二进制读写验证。验收材料包含迁移清单、兼容表、恢复演练结果与明确的不支持路径。

SQLite 和路径依据见 [资料来源](sources.md)；离线队列使用相同事务和迁移要求，见 [同步规范](offline-and-sync.md)。

用户删除与备份恢复后的删除状态核对见 [数据生命周期](privacy-and-data-lifecycle.md)；归档和路径威胁见 [安全设计](security-and-threat-modeling.md)。
