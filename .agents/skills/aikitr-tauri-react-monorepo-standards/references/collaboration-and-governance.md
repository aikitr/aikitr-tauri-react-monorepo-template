# 06 协作、规则治理与交付责任

适用：工程维护与生产交付。角色按实际团队映射到人/现有岗位；单维护者可以同时承担多个职责。规范定义团队流程，不能凭本技能推定已获部署、消息发送、远程配置或合并授权。

## GOV-CAPABILITY · 能力分级与负责人

| 项目状态             | 应具备的内容                                                         |
| -------------------- | -------------------------------------------------------------------- |
| 基础模板/原型        | 模块边界、真实脚本、可运行说明、现有能力的验证；未实现能力明确不适用 |
| 生产桌面             | 已启用的生命周期、数据恢复、诊断、性能预算、发行/更新与依赖治理      |
| 多应用/多人协作      | 共享契约与消费者矩阵、模块负责人、review/CI 规则、兼容与例外管理     |
| 身份/离线/多语言能力 | 启用对应章节的验收门禁；没有需求时不建设空系统                       |

**必须**为实际模块、持久化数据和发布产物确定所有者，明确谁维护接口、处理故障和评审变更。GitHub 项目可使用 CODEOWNERS，但仅存在该文件不会自动阻断合并；需要核对实际 ruleset/branch protection、权限和平台支持。代码所有者不等同于运行时授权。

## GOV-REVIEW · PR 与合并

- **默认**一份 PR 完成一个可审查目标；必要的依赖升级与消费者迁移可同行，避免把不相关目录迁移混进业务改动。
- **必须**说明问题/目标、受影响包与平台、公共契约变化、迁移或数据影响、实际验证及未验证项、恢复方式。低影响文案/样式按风险精简，不要求填写无关复杂表单。
- **团队生产协作默认**保护集成/发布分支，关键边界由相关维护者评审，所需 CI 通过且结果对应当前提交；过期结果不能证明新提交有效。具体人数和紧急修复方式由仓库制度明确，不臆造通用“两人审批”。
- **必须**让应运行的检查真实运行；被 skip、测试发现数量异常、缺少工具链或已知 flaky 都明确记录。隔离 flaky 测试应有负责人、范围、期限和替代验证，不把绿色但未执行当通过。

## GOV-EXCEPTION · ADR 与有期限的例外

**默认**将长期影响跨模块依赖、平台、协议、持久化、底座或发布方式的决定写入 `docs/adr/NNNN-<decision>.md`。最小字段：状态、背景与约束、选定方案、替代项和取舍、影响/迁移、决策负责人、日期及复查触发条件。普通局部实现选择无需 ADR。

**必须**给边界/预算/漏洞等例外记录：规则组 ID 与具体条款/等级、精确范围、原因、实际风险、补偿措施、负责人、相关工作项、到期或复查事件、退出条件。记录的是审查决定和后续责任，不能用全仓关闭检查、任意 eslint-disable 或长期 `skip` 代替。工具表达精确的允许范围，规则变更同时验证正常与违规样例。

例外到期必须产生可追踪的复查/纠正结果；团队可选择 CI 阻断或跟踪门禁，但不能无声自动延期。紧急发布仍记录采取的路径、未满足项和恢复/后续检查，不能靠重置基线或清空报告隐藏风险。

## GOV-RELEASE · 发布、运行维护与恢复

- **必须**把 commit/build ID、版本、平台/架构、产物 digest、签名结果、关键验证和数据兼容记录关联为一次发布。发布负责人检查的是已构建的候选产物，不能在验收后换一个未核对的安装包。
- **启用自动更新时**明确稳定/预发布等通道、更新签名验证、最低兼容版本、失败回退和数据迁移限制；灰度/暂停/回退按发布基础设施能力选择。二进制回退受 schema 兼容约束，见存储章节。
- **部署后端时**记录部署/配置版本、客户端兼容窗口、健康判定、回退与负责人；数据库迁移和 API 变更不能只对最新版客户端验证。
- **生产维护默认**为数据损坏、无法启动、更新失败、凭据泄漏/撤销和服务不可用建立适用的 runbook：检测→限制影响→恢复→确认→记录改进。仅有本地离线功能时采用对应的支持/恢复流程，不建立无需求的轮值制度。

## GOV-EVIDENCE · 统一验收记录

针对本次启用或修改的能力产出以下字段，作为评审/发布的证据入口：

`能力与场景 | 规则组 ID 与具体条款/等级 | 所有者 | 实际实现/范围 | 验证环境与命令/操作 | 结果与证据 | 未验证/不适用原因 | 例外及到期 | 兼容与恢复方式`

**必须**区分“规范要求、项目已实现、已经验证”。用户只授权规范时交付规则；授权实施时才修改对应项目。当前技能通过检查不表示项目已经企业级合规、启用了全部机器门禁或可以上线。

团队流程与技术边界衔接见 [工程交付规范](tooling-and-delivery.md)，相关平台行为见 [资料来源](sources.md)。

规则采纳、修订与七类可复用交付模板见 [落地与维护](standards-adoption-and-maintenance.md)；候选产物的环境/渠道记录见 [兼容与分发](platform-compatibility-and-distribution.md)。
